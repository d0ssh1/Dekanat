# Безопасность: модель угроз

Простыми словами для жюри — в конце документа. Техническая схема — `docs/architecture.md` §5.

## Что защищаем
| Актив | Почему важно |
|---|---|
| Профиль студента (ФИО, группа, зачётка, почта) | Персональные данные |
| Оценки и баллы | Личная информация об успеваемости |
| Заявки, вложения (паспорт, справка о доходах), готовые справки | Самые чувствительные документы |
| Пароли и сессии | Ключ ко всему остальному |
| Ключ GigaChat | Деньги и квота проекта |

## Угрозы и как закрыты

| # | Угроза | Как закрыта | Чем проверено |
|---|---|---|---|
| T1 | **Подставить чужой id в адрес** (`/documents/<id Даниила>`) | DAL: `where id = $id and student_id = <из сессии>` → 404. RLS в БД отрезает чужие строки даже при ошибке в коде | `tests/security/rls.test.ts`, IDOR-матрица Playwright (фаза 3) |
| T2 | Вызвать Server Action / API напрямую без интерфейса | Каждый action сам вызывает `requireStudent()` и zod-валидацию; id владельца не принимается извне | IDOR-матрица, аудит `security-auditor` |
| T3 | Забытая проверка в новом коде | RLS: без контекста роль `anon` → пусто. ESLint запрещает SQL вне DAL | тест «без контекста — пусто» |
| T4 | Утечка базы → пароли | argon2id (19 МиБ, t=2). Сессии хранятся как SHA-256 токена | тест «все хеши $argon2id$» |
| T5 | Перебор пароля | 5 попыток / 15 мин на логин+IP, в БД; одинаковый ответ и время для несуществующего логина | Playwright (фаза 3) |
| T6 | Кража сессии через XSS | cookie `__Host-` HttpOnly Secure SameSite=Lax; CSP с nonce; React экранирует вывод | заголовки в тесте (фаза 3) |
| T7 | CSRF | SameSite=Lax + проверка Origin у Server Actions (встроена в Next) | — |
| T8 | Кликджекинг | `X-Frame-Options: DENY`, `frame-ancestors 'none'` | — |
| T9 | Ключ ИИ в браузере или репозитории | Только env сервера, `.env` в `.gitignore`, gitleaks в CI, поиск значений в `.next/static` после сборки | CI |
| T10 | Опасный файл во вложении | Проверка сигнатуры (PDF/JPEG/PNG), ≤ 10 МБ, хранение вне `public/`, отдача как `attachment` + `nosniff` | фаза 6 |
| T11 | Помощник ИИ раскрывает чужие данные или действует сам | Инструменты получают Viewer из сессии; модель не передаёт id владельца; действия — только черновик + кнопка человека; лимит 30 сообщений/час | фаза 8 |
| T12 | Промпт-инъекция через текст заявки/объявления | Текст из БД передаётся модели как данные, инструменты всё равно ограничены Viewer | фаза 8 |
| T13 | Студент меняет себе баллы или статус заявки | RLS: запись баллов только `staff/system`; смена статуса — только сервисом сотрудника | тест «нельзя поставить себе баллы» |
| T14 | Публичная проверка справки раскрывает профиль | `/verify` вызывает `app.verify_document(code)` (SECURITY DEFINER): только номер, тип, даты и инициалы; код ≥ 16 символов | тест «короткий код — пусто» |
| T15 | Подменённый npm-пакет | Точные версии, lockfile, версии не моложе 14 дней, `npm audit` в CI | CI |
| T16 | Реальные персональные данные в прототипе | Сид только вымышленный, почты на домене `.test`, дисклеймер на сайте | ревью сида |

## Роли в БД
- `dekanat_owner` — владелец схемы: миграции и сид. Приложение им не пользуется.
- `app_user` — приложение. Не суперпользователь, нет `BYPASSRLS`, права только на нужные таблицы и колонки (`drizzle/0001_security.sql`).
- Контекст транзакции: `app.user_id` и `app.role` (`student | staff | system | auth | anon`).

## Простыми словами
- **Вход.** Пароль никогда не хранится как есть — только «отпечаток» по алгоритму argon2id, из которого пароль не восстановить. После входа браузер получает случайный ключ сессии в защищённой cookie, недоступной скриптам страницы.
- **Чужие данные.** Защита в два слоя. Код всегда спрашивает у базы «заявку с таким номером, *и чтобы она была этого студента*». А сама база дополнительно проверяет каждую строку: даже если программист забудет условие, студент получит пустоту, а не чужую заявку.
- **Ключи.** Ключ от GigaChat лежит только в настройках сервера. Браузер общается с нашим сервером, а уже сервер — с GigaChat.
- **Данные.** Все люди, оценки и заявки придуманы.
